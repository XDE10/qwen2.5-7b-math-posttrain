## A. 项目总览

**A1. 为什么选 Qwen2.5-7B-Instruct 做底座，不用 Qwen2.5-Math-7B 或 R1-Distill？**
Qwen2.5-Math-7B 是做过约 1T token 数学继续预训练的专用底座，只支持 4K 上下文，装不下 16K–32K 的长链轨迹；R1-Distill 已经蒸馏过 80 万条 R1 数据，再在上面做 1000 条 SFT 很难说清增益来自哪里。通用 Instruct 模型更能回答"少量长链数据能把通用模型推多远"，也和 s1.1-7B、QFFT 论文的设定一致，可以直接拿公开结果当锚点。代价是起点低：E0 在 AIME 上只有【待填】%。

**A2. 你的工作和 s1 / QFFT 论文比，新东西在哪？**
三点。一是教师：用 DeepSeek-V4.1-Flash 重新造了 1000 题轨迹，和 R1 轨迹在同一题集、同一管线下做受控对比，这是两篇论文都没做的。二是 QFFT 接 RL：QFFT 论文到 SFT 为止，我在 QFFT 模型上做 GRPO，并观察 RL 会不会破坏它按难度分配长度的性质。三是不截断：官方 QFFT 用 16K 截断，1000 条 R1 轨迹里有 90 条会在给出答案之前被截掉，我把窗口提到 32K，保证每条训练序列都有结尾。

**A3. 单卡资源下怎么排实验优先级？**
先保证"尺子"对：修判分器、改连续批处理、去 YaRN，并先评测公开 QFFT 权重，确认我的评测能复现论文量级。然后按研究问题的价值排：QFFT vs SFT（主结论）→ GRPO（RL 岗位核心）→ 教师对比 → RL 起点对比。所有阶段在 Drive 上留完成标记，失败后重跑同一条命令即可续上，算力不浪费在重复劳动上。

**A4. 如果结论是 QFFT 不如 SFT，或者 RL 没涨分，你怎么写？**
照实写，并给出机制解释。例如 QFFT 若在 AIME 上掉点，可以看长度–难度曲线：如果难题上 QFFT 没触发长链（反思词触发率低），说明自适应机制在 7B 上触发不足。RL 若不涨分，就看 pass@k：pass@1 不动而 pass@16 也不动，说明题池对模型太难或太易（零方差组比例高）；pass@1 涨而 pass@16 降，就是"磨尖"。负结果加机制分析，比报一个没有置信区间的 +1pp 更有说服力。

**A5. 为什么只跑单种子？**
算力约束。单种子下我用按题配对 bootstrap 给出 CI，并把 AIME24+25+AMC23 合并成 100 题提高统计功效。同时承认这只覆盖了评测采样的方差，没覆盖训练随机性；若时间允许，优先给主线 `qfft_ds` 补第二个种子。

## B. 数据

**B1. 为什么不直接用 s1K-1.1 的 R1 轨迹？**
用了，它是对照组。新造 DS 轨迹有三个原因：一是想回答"换一个更新、更省 token 的教师，学生会不会更好"；二是 R1 轨迹固定，没法按需重采样，而 DS 可以对答错的题继续采样（`ds_verified` 变体）；三是 DeepSeek 新模型的轨迹更短（12 题试点平均 4,181 vs 7,409 token），训练更便宜。

**B2. 准入规则是什么？为什么不按答案正确性过滤？**
正常结束（`finish_reason == "stop"`）、思考和最终回答都非空、SFT 编码后 ≤ 32768 token。不按对错过滤有三个理由：s1K-1.1 的 742 道可核对题里约 37% 的 R1 轨迹被自动判错，仍全部保留，QFFT 官方也没过滤，保持一致才能和公开结果对比；1000 题里有 258 题是证明题或参考答案无法自动核对，按对错过滤会系统性偏向可核对的计算题；Li 等人（2025，"Structure, not content, is what matters"）发现长链 SFT 学到的主要是推理结构，用答案错误的轨迹训练只比全对轨迹低 3.2%。正确率作为元数据记录，`ds_verified` 作为消融。

**B3. 超长轨迹怎么处理？截断、丢弃、扩窗口各有什么问题？**
截断：序列在答案之前被切掉，模型学到"长推理不收尾"，这与 v26 观察到的重复循环方向一致。丢弃：被丢的是最难的题（DS 首轮 1000 题里 164 条完整轨迹超过 16K，另有 89 条不完整：88 条长度耗尽、1 条缺最终回答），训练集变简单，AIME 收益会被低估。扩窗口：显存和时间成本上升。我选扩到 32K：R1 最长 26,835 token 全部放得下；显存用 Liger 消掉 logits 那一大块后，G4 和 H100 都有余量；时间按 token 线性增长，可以接受。

**B4. 去污怎么做，发现了什么？**
按 Qwen2.5-Math 报告的思路：文本规范化（小写、去 LaTeX 命令、去标点）后用 13-gram 找候选，再用序列相似度 ≥ 0.6 过滤，对 MATH-500、AIME24、AIME25、AMC23、GSM8K 全部检查。命中 17 对：3 对是早已替换掉的精确重复；1 对是新发现的泄漏，s1K-1.1 第 918 行（AIME 2002 I #12）和 MATH-500 `test/intermediate_algebra/1063.json` 是同一题换问法，R1 轨迹里直接算出了 MATH-500 的答案 1+274i，我用原题池里已批准的题替换了它；其余 13 对只是"m/n 互素，求 m+n"这类模板句式相同。每对的判定和理由都写进了复核文件，新增未复核的命中会让构建直接失败。

**B5. 你怎么判断 DeepSeek-V4.1-Flash 的轨迹质量不比 R1 差？**
分两层。数据层：在同一批可核对题上比较两位教师的最终答案正确率、对错矩阵、长度和反思词频率；R1 在 742 道可核对题上是 62.7%，DS 是【待填】%。训练层：同题、同配方训练两组学生，看评测结果。教师正确率高不等于学生更强：轨迹的可学性（长度、跳步多少、风格一致性）对 7B 学生同样重要，所以最终以学生评测为准。

**B6. "按时间顺序取第一次可用尝试"在防什么？**
防止选择偏差。如果对每题采样多次再挑最短或答对的那条，DS 组就得到了 R1 组没有的"挑选"，比较就不公平；而且挑最短会把长度偏好直接写进数据。第一次可用尝试相当于"采一次，失败才重采"，所有题、所有轮次用同一条规则。答对筛选只放在单独的 `ds_verified` 变体里。

**B7. 教师 API 造数遇到过哪些工程问题？**
流式断连、服务端 5xx、请求是否已计费未知、Windows 原子写偶发失败、额度耗尽切换供应商。v93 的做法：每次尝试一个独立目录，请求先落盘再发送，逐 chunk 写日志；结果未知的尝试不复用，直接用下一个尝试编号（成本不是约束，正确性和可追溯更重要）；密钥只从环境变量或私密文件读取，日志里做脱敏。

## C. SFT / QFFT 原理

**C1. QFFT 到底改了什么？训练序列长什么样？**
只改训练序列。SFT 是 `system + user(题目) → assistant(思考 + "\n<|im_start|>answer\n" + 最终回答 + <|im_end|>)`，只对 assistant 部分算 loss。QFFT 去掉题目和所有 chat 标记，只剩 `思考 + "\n<|im_start|>answer\n" + 最终回答`，不加 EOS，对全部 token 算 loss（官方 `qwen_qfft` 模板就是三个 `{{content}}`）。推理时两者完全一样，都用正常的 chat prompt。

**C2. 为什么去掉题目能让模型"自适应"？**
SFT 学的是"在这种题目条件下输出长链"，题目到长链的映射会覆盖原 Instruct 模型"题目到短 CoT"的行为，于是简单题也长篇大论。QFFT 不在题目上做条件化，模型学到的是长链推理文本本身的分布（反思、验证、回溯这些模式），而"看到题目先怎么答"仍保留原模型的短 CoT 习惯。推理时模型先按短 CoT 走，遇到不确定时生成出"Wait""let me check"这类片段，就进入了它在 QFFT 中学过的长链模式。论文在 7B 上平均少用约 50% token，准确率基本持平。我用 GSM8K 与 MATH-500 分难度的长度和反思词触发率来验证这个机制：【待填：SFT 曲线接近水平，QFFT 随难度上升】。

**C3. QFFT 训练时没有 EOS，推理为什么还能停？**
QFFT 从不在 chat 格式的位置上更新，`<|im_end|>` 的生成行为来自原 Instruct 模型，没有被覆盖；模型写完最终回答后仍按原习惯输出 `<|im_end|>`。风险是训练把分布推得太远导致不停止，所以我监控截断率和尾部重复率：【待填：QFFT 截断率 x% vs SFT y%】。

**C4. loss 掩码怎么做？两种格式的监督 token 差多少？**
SFT：prompt 部分 label 置 -100，response 和 `<|im_end|>` 监督。QFFT：label 等于 input_ids，全部监督（第一个 token 因为因果移位没有预测目标）。两者 response 的 token 完全相同（我在 CPU 上逐 token 验证过），所以监督量只差每条 1 个 `<|im_end|>`：12 条样本的冒烟测试里 QFFT 3,239 个监督 token，SFT 3,251 个。这让两组的"有效训练量"几乎相等，比较是干净的。

**C5. 梯度累积下 loss 怎么归一化？长样本会不会主导梯度？**
Transformers 4.46 之后会把整个累积 batch 的有效 token 数传进 loss，loss = 全部监督 token 的交叉熵之和 / 总 token 数，等价于 token 级平均；修复之前每个 micro-batch 先各自平均再相加，短样本被放大。token 级平均意味着长样本贡献更多梯度，这是 s1 和 QFFT 的默认做法，两组相同，所以不影响比较；如果想让每题等权，可以改成按样本平均，那是另一个配方。

**C6. 为什么 6 epoch、LR 1e-5？1000 条会不会过拟合？**
跟 QFFT 官方一致（6 epoch、1e-5、cosine、10% warmup、wd 1e-4），s1.1-7B 是 5 epoch。小数据长链 SFT 的目标本来就接近"记住推理格式和模式"，多 epoch 是常见做法；过拟合风险体现在熵下降、输出多样性变差，这会直接影响后续 RL 的探索，所以我在 RL 前测 pass@16。不按 dev 挑 epoch，避免拿测试集调参。

**C7. 长链 SFT 后为什么会出现重复循环？**
常见原因：训练窗口短于推理预算，模型没见过很长之后怎么收尾；贪心解码放大了自我强化的循环；训练数据里本身有截断、无结尾的样本；模型学到了"Wait, let me re-check"的表面模式，却没学会判断何时已经足够。我的证据：v26 的 dev 截断样本里 118 条尾部有精确重复；16 题控制对照里采样比贪心截断略少（原生 9→8 条、YaRN 6→5 条），样本太小，只能算方向性证据。v93 的应对：32K 窗口不截断、评测用 temperature 0.6、报告尾部重复率。

## D. 单卡全参工程

**D1. 7B 全参在单卡上的显存账？**
Qwen2.5-7B 有 7.62B 参数。GPU 上：bf16 权重 15.2 GB + bf16 梯度 15.2 GB。优化器若放 GPU 还需要 fp32 主权重 30.5 GB + Adam m/v 61 GB，总共超过 120 GB，单卡放不下，所以用 ZeRO-2 把优化器卸到 CPU。激活：开梯度检查点后每层只存输入隐状态，32K × 3584 × 2 B × 28 层 ≈ 6.6 GB，加单层重算的 MLP 中间张量约 5 GB。最大的隐藏项是 logits：32K × 152K 词表 × 2 B ≈ 10 GB，升 fp32 再算梯度会到 30–40 GB，Liger 的 FusedLinearCrossEntropy 分块计算把它基本消掉。实测：v46 在 16K、无 Liger 时峰值 46.6 GiB；v93 32K 的峰值【待填】GiB。这个数来自按最坏情况设计的冒烟：32 条每条恰好 32,768 token 的序列，而不是随机抽几条真实样本（真实数据长尾明显，随机抽样大概率测不到峰值）；GRPO 冒烟同理，用 vLLM 的 `min_tokens` 把每条 completion 强制生成到 8192 token。

**D2. 为什么 ZeRO-2 + CPU offload，不用 ZeRO-3？**
ZeRO-3 的收益来自把参数切到多张卡上，单卡没有可切的对象，只有再开参数 offload 才省显存，代价是每层前向和反向都要从 CPU 拉参数，慢很多。ZeRO-2 + 优化器 offload 让 bf16 权重和梯度留在 GPU，只把 fp32 主权重和 Adam 状态放在 CPU，单卡上是速度和显存的最好折中。QFFT 官方在 8 卡上用 ZeRO-3 offload，情况不同。

**D3. Liger 的 FusedLinearCrossEntropy 省了什么？**
把 lm_head 矩阵乘和交叉熵融合，按序列分块计算，每块算完 logits 立刻求 loss 和梯度再丢弃，不再物化完整的 [序列长度 × 词表] logits 及其 fp32 副本和梯度。Qwen 的 15 万词表让这一项在长序列上特别大。另外 Liger 还融合了 RMSNorm、RoPE、SwiGLU，省一些激活和带宽。

**D4. 梯度检查点的代价？**
前向多算一遍，单 token 计算从约 6N 增加到约 8N FLOPs（N 为参数量），慢约 30%；换来激活显存从"每层所有中间张量"降到"每层一个隐状态 + 一层重算的峰值"。长序列下不开基本放不下。

**D5. CPU offload 的瓶颈在哪？怎么缓解？**
每个 optimizer step 要在 CPU 上更新 7.6B 个参数，并在 PCIe 上来回搬约 30 GB（梯度下去、参数上来），耗时取决于 CPU 核数，与 GPU 无关。缓解：把有效 batch 从 8 提到 16，optimizer step 数减半，CPU 时间摊到更多 token 上；梯度累积不增加 CPU 开销；不开 pin_memory 以免 122 GB 状态锁住主机内存。实测每步【待填】秒，其中 CPU 部分约【待填】秒。

**D6. 检查点为什么有 122 GB？怎么做到"真续跑"？**
bf16 模型 15 GB + DeepSpeed 的 bf16 模型状态 15 GB + fp32 主权重和 Adam m/v 共 91 GB。只存模型权重不能续跑：优化器动量、LR 调度位置、随机数状态、数据采样顺序都会丢，相当于热启动。v93 每约 1 epoch 存一次完整检查点到本地 SSD，再在后台限速镜像到 Drive，并写完成标记；新 VM 启动时自动拷回最新的完整镜像，由 HF Trainer 恢复优化器、调度器、RNG 和 dataloader 位置。我在 CPU 上模拟过"第 2 步存档后 VM 丢失"，新进程从 Drive 恢复后 LR 正好接在 7.5e-6 继续，和不中断时一致。

**D7. 在 Colab 这种不可靠环境下，工程上有哪些保证？**
所有状态在 Drive：训练镜像、逐条生成记录、判分记录、阶段完成标记；每个阶段幂等，重跑即续。依赖分环境：训练用镜像自带的 torch（与系统 CUDA 一致，DeepSpeed 编 CPU-Adam 需要），推理和 RL 用独立 uv 虚拟环境，首次装好后快照到 Drive。生成和判分解耦，GPU 上只生成，判分在 CPU 做，一个病态输出不会卡住 GPU。每个 run 有身份文件，配方或数据变了拒绝续跑，防止把两个实验拼在一起。调度上，任务跑在 VM 的 kernel 里，本地断线只会让启动脚本改为轮询 VM 上的日志，不会杀掉任务；反过来这也意味着用户可能在旧任务还在跑时重新启动同一阶段，所以每个阶段的 Drive 标记带心跳，第二台 VM 在心跳新鲜时直接拒绝，避免两台机器写同一个检查点目录。

## E. LoRA vs 全参

**E1. 为什么 SFT 用全参、RL 用 LoRA？**
信息量不同。SFT 每条样本提供约 O(token 数) 比特的监督，1000 条 × 1 万 token 量级，需要较大容量去写入一种新的推理行为；策略梯度每条 rollout 只带来约 1 bit（这条对还是错），150 步 × 64 条 ≈ 1 万比特，rank 32 的 LoRA 容量绰绰有余。Thinking Machines 的实验显示 RL 下 rank 1 都能追平全参。工程上，单卡 GRPO 用 LoRA 不需要第二份全参优化器状态，β=0 时也不需要参考模型，vLLM 同步的是合并后的权重。

**E2. LoRA 的 LR 为什么大约要 10 倍？**
LoRA 的更新是 ΔW = (α/r)·BA，B 初始化为 0，训练初期的有效步长远小于直接更新 W；按 1/r 缩放时最优 LR 近似与 rank 无关，实验上稳定在全参最优 LR 的 10 倍左右，短训练甚至更高。很多人把全参的 LR 直接搬给 LoRA，然后得出"LoRA 不行"的结论，我的 v26 就踩了这个坑。

**E3. LoRA 挂在哪些层，rank 怎么选？**
挂所有线性层，尤其 MLP：MLP 占大部分参数，只挂注意力即使参数量对齐也明显更差。rank 由需要写入的信息量决定，RL 用 16–32 足够；SFT 若要用 LoRA，rank 64 以上、LR 1e-4、batch 不要太大（LoRA 对大 batch 更敏感），dropout 0。

**E4. v26 为什么掉点？能确定是 LoRA 的锅吗？**
不能。v26 同时存在四个差异：LoRA 且 LR 偏低、8K 训练窗口配 32K 推理、AIMO2 数据（有无 think 标签混杂、只保留 8K 内的轨迹）、静态 YaRN。评测侧还有判分器偏差。v93 一次改掉了大部分，结论只能是"组合起来的效应"。如果想单独回答 LoRA 的问题，最省的实验是在同一份 QFFT 数据上加一组 LoRA r64、LR 1e-4，和全参比准确率与长链触发率。

## F. RL / GRPO

**F1. 写出 GRPO 的目标，优势怎么算？**
对每题采样 G 个回答，奖励 r_i，组内优势 A_i = (r_i − mean(r)) / std(r)，序列内每个 token 共享 A_i。目标 J = E[(1/G) Σ_i (1/|o_i|) Σ_t min(ρ_{i,t} A_i, clip(ρ_{i,t}, 1−ε, 1+ε) A_i) − β·KL(π_θ‖π_ref)]，ρ 是新旧策略概率比。KL 常用 k3 估计 π_ref/π_θ − log(π_ref/π_θ) − 1。这些公式我在 `src/losses/reference.py` 里写了参考实现和单元测试（全同奖励时优势为 0、长度归一化对梯度的影响、clip 行为）。

**F2. 相比 PPO，GRPO 省了什么，代价是什么？**
省掉价值网络：基线来自同题的组内平均，不需要训练 critic，显存和工程都省一半。代价是每题要采样多条（G 通常 8–64），生成成本高；只有序列级优势，没有逐 token 的信用分配；组内奖励全相同时这组没有梯度，浪费采样。

**F3. Dr.GRPO 和 DAPO 分别改了什么？你用哪个？**
Dr.GRPO 指出两个偏差：按 1/|o_i| 做长度归一化，会让答错的长回答每个 token 受到的惩罚更小，助长"错了就写长"；按 std 归一化，会放大太简单或太难的题。它改成用常数（如最大长度）归一化、去掉 std。DAPO 有四项：clip-higher、动态采样（丢掉全对或全错的组再补采）、token 级损失（按整个 batch 的有效 token 数归一化）、超长样本过滤或软惩罚。我用 TRL 的 `loss_type="dapo"`（token 级归一化，消除了 1/|o_i| 的长度偏差）+ clip-higher + 截断掩码，保留 group 级 std 缩放；动态采样 TRL 没有现成实现，我用 `frac_reward_zero_std` 监控，比例过高就换题池。

**F4. 为什么 β=0？去掉 KL 有什么风险？**
DeepSeek-R1 之后很多可验证奖励的 RL 配方都去掉了 KL：奖励是规则判分，不存在奖励模型被利用的问题，KL 主要起正则作用；去掉后不必加载参考模型，省显存和一次前向。风险是策略漂移过大、熵塌缩、长度失控。我监控熵、平均长度（分对错）、clip 比例和评测集的 pass@k；LoRA 本身也限制了漂移幅度。

**F5. clip-higher 是什么？**
PPO 的对称裁剪 [1−ε, 1+ε] 对低概率 token 很不公平：概率 0.01 的 token 最多只能涨到 0.012，而高概率 token 几乎不受限，结果探索性的低概率 token 很难被强化，熵快速下降。DAPO 把上界单独放大（ε_high = 0.28，下界仍 0.2），让正优势的低概率 token 有更大的上升空间，缓解熵塌缩。

**F6. 截断的 completion 为什么要从 loss 里去掉？**
被 max_completion_length 截断的回答没有最终答案，奖励为 0，但它不一定是错的推理，只是没写完；把它当负样本会惩罚"思考得长"，把模型推向过早作答，也会给长度引入噪声。去掉它们（DAPO 的超长过滤）只是不更新，不扭曲信号。代价是如果截断很多，有效样本变少，所以 QFFT 起点的短输出在这里有优势。

**F7. 零方差组是什么，怎么处理？**
一组 G 个回答奖励全相同（全对或全错），组内优势全为 0，对梯度没有贡献，生成算力白花。原因是题对当前模型太易或太难。处理：选题时按模型的通过率筛到中间难度（我用 E0 的 1–3/4 和 0/4 两个池，SFT 后模型变强，所以加了 0/4 的难题）；训练中监控 `frac_reward_zero_std`，超过 0.6 就换池或做动态采样。

**F8. vLLM 生成和训练的 logprob 不一致怎么办？**
推理引擎和训练框架的 kernel、精度不同，同一序列在两边算出的 logprob 有差异，等于在用一个略不同的策略采样，是隐性的 off-policy。TRL 默认开启重要性采样修正（1.17 默认 `sequence_mask`：序列级比值超过 3.0 的整条序列不计入 loss），并记录两边 logprob 差的均值和最大值；差值持续变大就要检查权重同步是否出错。

**F9. 奖励怎么设计？有没有 reward hacking 风险？**
最终段（`<|im_start|>answer` 之后）最后一个 `\boxed{}` 与参考答案用 Math-Verify 比较，对就是 1，否则 0，不加格式奖励（SFT 后格式已稳定）。可能的利用方式：在最终段写多个框碰运气——我只取最后一个框，多框拼接只用于"求所有解"类题，且需要整体等价；在思考里写一堆答案——思考部分不判分。判分基础设施失败超过 5% 直接中止训练，不把它当错。

**F10. RL 的提升是新能力还是磨尖？**
看 pass@k 曲线。Yue 等人（2025）发现可验证奖励 RL 主要提高 pass@1，k 较大时基座的 pass@k 反而更高，说明 RL 是把概率质量集中到已有的正确路径上，而不是扩大能力边界。我在 AIME/AMC 上画 k = 1…16 的 pass@k：【待填】。如果大 k 端也上升，说明在这个规模下 RL 带来了基座采样不到的解法；如果只有小 k 上升，就是磨尖。

**F11. RL 题池选 E0 的 1–3/4 和 0/4，对 SFT 后的模型还合适吗？**
不完全合适：E0 的中等难度对 SFT 后更强的模型可能偏简单，所以把 E0 四次全错的 637 题也放进来，整体难度上移。理想做法是用 RL 起点模型重新测通过率再筛，成本约 1–2 GPU 小时，可作为预算充裕时的改进；当前用零方差组比例作为是否需要重筛的判据。

## G. 评测与统计

**G1. 评测口径是什么？为什么不用贪心？**
所有模型同一组 prompt token，原生 RoPE，上下文 32768，temperature 0.6、top_p 0.95，逐条固定种子；AIME 各 16 次、AMC 8 次、MATH-500 4 次、GSM8K 1 次。不用贪心：长链模型在贪心解码下更容易陷入重复（R1 也建议 0.5–0.7），而且单次贪心无法估计方差和 pass@k。QFFT 论文的 32K × 16 也是采样口径。

**G2. mean@16、pass@16、maj@16 的区别？**
mean@16：每题 16 次的平均正确率，再对题目平均，是 pass@1 的估计。pass@16：16 次里至少对一次的概率，用无偏估计 1 − C(n−c, k)/C(n, k) 计算，衡量能力上限。maj@16：16 个答案按等价性聚类，取票数最多的那类是否正确，衡量自洽性。三者回答不同问题，不能混用，例如 RomEscape 作者报告的 SFT-7B MATH-500 80.9 是 16 次采样的 mean@16，不是 pass@16。

**G3. AIME 只有 30 题，怎么判断差异显著？**
题目层面的方差占主导：一道题从 0/16 变成 8/16，平均正确率就变 1.7pp。我按题做 bootstrap 给 95% CI，比较两个模型时用按题配对 bootstrap（差值的 CI 和 p 值），并把 AIME24+25+AMC23 合并成 100 题作为主指标。经验上单个 AIME 年份差 5pp 以内都不显著。

**G4. 为什么只判最终段？严格判分器的问题是什么？**
长链模型常在思考过程中写出中间答案并加框，后来发现错误再改正。旧的严格判分器抽取全文所有框，只要有两个不同的框就判错，等于惩罚自我纠错；它还把 `x=5` 这类关系式一律判为不支持。这会系统性压低长链模型、偏向只写一个框的 E0。dev256 上严格判分比原生 Math-Verify 低 18 题（7pp）。v93 只判最后一个 answer 标记之后的最终段、取最后一个框，思考部分不参与。

**G5. 主指标为什么不用 LLM 复核？**
之前的做法是只把自动判错的样本交给 DeepSeek 复核，复核只能把错改对，不能把对改错，是单边修正；格式越差的模型补回越多。实测：同一口径下公开 SFT-7B 补回 17 条、QFFT-7B 补回 6 条，原生判分两者都是 389/500，而复核后变成 81.2 vs 79.0，差距全部来自复核。确定性判分可复现、可审计，LLM 复核只放在错误分析里。

**G6. 和 Qwen2.5-Math-7B-Instruct 怎么公平比较？**
它只支持 4096 位置，不可能用 32K 预算评测，所以按它自己的上下文、同样的采样参数评测，作为外部参考而不是受控对照。还要说明背景差异：它在 1T token 以上数学继续预训练的底座上，用约 250 万条 CoT SFT（另有工具推理数据）和"奖励模型 + 规则判分"的 GRPO 训练；我的卖点是用 1000 条 SFT 在通用底座上做到【待填】，即数据效率，而不是绝对分数。

**G7. YaRN 为什么去掉？**
Qwen2.5-7B-Instruct 原生支持 32768 位置，32K 内不需要外推。vLLM 的 YaRN 是静态的，对所有长度都生效，官方说明它可能影响短文本表现；训练时又没用 YaRN，推理时开启是训练–推理不一致。v93 统一原生 RoPE、上下文 32768。要主动说明一个反例：v39 的 16 题对照里 YaRN×4 + 采样的截断反而最少（5/16，原生采样 8/16），但 16 题单次采样分辨不出这种差异，我把它当作"YaRN 不是已证实的根因"，而不是"YaRN 更好"。v93 的评测会报告截断率，截断率高再补一组 YaRN 对照。

## H. 调试与失败分析

**H1. 讲一个排查得最深的问题。**
用 0.4 节的 RL 奖励静默为 0。要点：现象（loss 与 grad_norm 恒为 0、`frac_reward_zero_std` = 1）→ 根因（模块路径变化 + 宽泛的异常捕获把基础设施失败折算成答错）→ 修复（报错而不是吞掉）→ 机制化（训练中判分失败率超过阈值直接中止，并加进监控清单）。

**H2. v26 的回退怎么定位的？**
用 0.3 节。强调方法：先看现象的分布（截断占比、尾部重复），再做小规模控制对照（RoPE × 解码），再审计尺子（判分器），最后找外部锚点（同口径评测公开 checkpoint）区分"方法"和"实现"。

**H3. 怎么确认自己的 QFFT 实现和官方一致？**
四层证据。数据：我的 response 拼接方式对 s1K-1.1 重建出的 1000 条与官方 S1_QFFT 数据逐字相同。编码：QFFT 的 labels 等于 input_ids、末尾没有 EOS；SFT 的 target token 与 QFFT 的 token 完全相同，只多一个 `<|im_end|>`。配方：LR 1e-5、6 epoch、cosine、10% warmup、wd 1e-4、AdamW 默认 betas 与官方 yaml 一致，差异只有有效 batch 16（官方 8）和 32K 不截断（官方 16K 截断），并写明理由；系统层面用单卡 ZeRO-2 + DeepSpeed CPU Adam 代替 8 卡 ZeRO-3 offload，优化算法相同。评测：先用我的评测管线跑官方 QFFT-S1-7B，结果【待填】与论文（MATH 80.2、AIME25 17.2）同一量级，说明尺子没问题。

**H4. 训练 loss 怎么判断正常？**
初始 loss 应与公开 s1.1-7B 的 TensorBoard 日志同一量级（相同底座、相近数据）；SFT 与 QFFT 的 loss 不可直接比较（QFFT 的序列开头没有题目，前几百个 token 更难预测）；loss 在 epoch 边界出现台阶式下降是多 epoch 记忆的正常表现；grad_norm 长期为 0 或 NaN 要立即停。

## I. 开放题

**I1. 如果有 8 张卡，你会怎么改？**
训练：ZeRO-3 分片，不再 CPU offload，optimizer step 从十几秒降到亚秒级，可以做 LR 和 epoch 扫描以及多种子。RL：vLLM 用独立的推理卡（server 模式），训练和生成异步流水；每步更多题、更大的 G，加上动态采样；训练几千步而不是 150 步。评测：每个模型多种子，报告训练随机性带来的方差。

**I2. 怎样进一步压缩推理长度而不掉点？**
RL 里加长度相关的奖励或惩罚（只对答对的回答按长度给分，或按预算条件化的长度控制）；用 Dr.GRPO 式归一化去掉"错了写长"的偏差；推理时的预算控制（s1 的 budget forcing 可以强制收尾或延长）；数据侧用更短的教师轨迹（DS 本身就短）。要同时报告准确率–token 曲线，单看长度没有意义。

**I3. QFFT 和 RL 结合还有什么可研究的？**
QFFT 的短输出让 RL rollout 便宜，同样 GPU 时长能跑更多步，这是一个可以量化的"初始化影响 RL 效率"的问题（RQ4）。另一个方向是 RL 是否会抹掉自适应长度：标准 GRPO 倾向于让长度增长，可以比较 GRPO 与 Dr.GRPO 下长度–难度曲线的变化。还可以把"是否进入长链模式"当作可学习的决策，用 RL 显式奖励"简单题短答、难题长想"。

**I4. 小数据长链 SFT 对 7B 的上限怎么看？**
s1 和 LIMO 的观点是预训练已经有了知识，少量高质量长链数据主要是激活推理格式。这在 32B 上很明显；在 7B 上收益要小得多（QFFT 论文 7B 的 AIME25 约 17%–18%），而且有研究发现更小的模型用少量长链数据训练会先掉点。我的结果【待填】。要再往上，通常需要更多数据（数万到数十万条）或更长的 RL。

**I5. 项目有哪些局限？**
单种子；RL 只有 150 步；题池难度没有按 RL 起点重新筛；教师对比只有一种新教师；Qwen2.5-Math 只能在 4K 下比较；评测只覆盖数学，没有测通用能力的遗忘（可以补 IFEval）。这些都写在报告的局限性一节里。
