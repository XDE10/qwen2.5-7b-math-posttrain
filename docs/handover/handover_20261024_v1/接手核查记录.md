## 2. 实际数据与代码流：为什么检查这些位置

### 2.1 JSONL → 文件授权 → 模型字段

两个入口只有两行，分别调用 `cli('sft',False)` / `cli('rl',False)`。`src/training/approved_hf.py:161-165` 检查 stage/模态，再到 `run:90-91`、`approved_config:15-29`。

`src/data/approved_training_inputs.py:6-17` 依次检查训练白名单、目录逃逸、文件 SHA、非空且每行 training_approved is True、sample_id 唯一。SHA 是封存身份，不是质量证明；只改行批准字段会破坏文件 SHA，只改 SHA 也不能代替审批。`model_view:20-34` 构造新的白名单字典；数学 SFT 只取 problem 为输入、solution 为监督。reference_answer 与审核字段不进入提示。

本轮还独立复核 1441 个保护 ID：256 道 math_dev 的 ID 全部包含其中。两臂与候选池对保护 sample_id 无交集，与 dev/MATH-500/GSM8K-test 的规范化精确题面 hash 无交集；评测三文件行数 256/500/1319、SHA 与 math_manifest 一致。规范化规则来自 `src/data/prepare_math_data.py:21-28`。跨来源 ID 不能独立识别同题，因此同时查题面 hash；本轮没有重跑近重复 Jaccard、同构题或人工语义审核，不能声称零污染。

注意：loader 本身没有读取 protected_dev_ids_file，也没断言 split=train；离线迁移脚本同样没有主动核对保护交集。这是防线缺口，当前封存数据的本轮检查通过，不等于未来换版本也有运行时保证。

### 2.2 白名单 → chat template → input_ids / labels

`src/training/approved_hf.py:42-50` 使用固定 system 指令、user problem；prefix 开启 add_generation_prompt，full 添加 assistant solution 后关闭。prefix 必须是 full 的严格前缀，full 必须不超过 max_length 且回答非空；否则直接抛错，**没有静默截断**。不应通过截断掉末尾答案来“解决”该错误，应检查 tokenizer/API 和数据预算。

令第 i 条 prefix 长 Pᵢ、完整长 Lᵢ：input_ids 为 full；labels 为 `[-100]×Pᵢ + full[Pᵢ:]`。训练把它解释为每个位置的目标 token；prompt 仍参与上下文计算，只是不作为监督目标。不能把“prompt 的预测位置无直接 loss”说成 prompt embedding 或共享参数无梯度。

本轮用本地真实 tokenizer 复算两臂全部样本，序列上限分别 3876≤4096、1443≤3800。原生有 4 条超过 3800，但 raw SFT 当前上限是 4096，所以未超预算。两臂所有样本前缀和长度检查通过，监督区均含 EOS。完整序列 token 总量为 3,676,090 / 519,989；监督 token 为 3,516,983 / 360,882，原生约为精炼的 9.75 倍。这里是各样本遍历一次的静态 token 总和，**不是已训练 token，也不是正式 run 的实际消耗**。

重要环境限定：计数环境为 helloAgents Python 3.11 / Transformers 5.18.0 / tokenizers 0.23.2，只做只读诊断。该版本 apply_chat_template 默认返回 BatchEncoding，而当前 encode_sft 按 list 使用；直接调用现有 encode_sft 确实抛 prefix/length violation，两臂均失败。这不是实际样本超长：本轮审计显式取 input_ids，并用只作用于审计的 return_dict=False 包装器重新调用原 encode_sft 验证等价。生产源码未改，项目记录的 Transformers 4.57.6 环境仍需重新建立和验收。证据：[token_audit.json](token_audit.json) 的 entry_encode_sft、violations、encode_with_explicit_list_api 与 tokenizer 返回类型。

### 2.3 padding、EOS 与 next-token shift

`CompletionCollator:32-39` 按当前 batch 的最长 N 右侧补齐，产生 input_ids/attention_mask/labels，形状均为 `[B,N]`。真实 token 的 attention=1，pad 的 attention=0、label=-100。最长与最短样本组成的实测诊断 batch 分别为 `[2,3876]`、`[2,1443]`，padding labels 的断言通过。正常配置 batch=1，这里 B=2 仅用于暴露 padding 错误。

`approved_hf.py:112-113` 从本地 tokenizer 读取 EOS/pad：本轮为 EOS=151645(`<|im_end|>`)、pad=151643(`<|endoftext|>`)。SFT 右 padding，RL 左 padding。EOS 由 chat template 添加，不是 encode_sft 手动追加；模板在 EOS 后还有换行 token 198，labels 也监督这个换行。最长样本尾部 ID 已保留在 token_audit.json。不要按 token ID 一刀切屏蔽所有 EOS：那会连真实结束监督也删除；本 collator 按补齐位置屏蔽。

模型 logits 为 `[B,N,V]`。实际 HF Trainer 把 labels 传给 causal LM，由模型内部做 shift，项目没有预先手工错位。独立参考 `src/losses/reference.py:10-14` 明确计算 logits[:, :-1] 对 labels[:, 1:]，展平为 `[B(N-1),V]` 与 `[B(N-1)]` 后做忽略 -100 的交叉熵。第一个回答 token 在 P 位置，它由 P-1 的 logits 预测；EOS 同样是有效目标。`tests/test_losses_and_masks.py:11-19` 用 `[1,7,8]` 微型张量检查对应梯度，本轮该测试在默认环境通过；这不等于 7B forward/backward 通过。

### 2.4 SFT 保存 → 合并基座 → 新 RL LoRA → reference

`approved_hf.py:110-125` 加载 BF16 模型，SFT 注入 LoRA；当前实现 r=16/alpha=32/dropout=0，目标覆盖注意力与 MLP 投影。dropout=0、LR=2e-5 是现有实现/配置，不能误用历史方案 0.05 或更低 LR 描述它。

`approved_hf.py:152-157` 保存 final adapter，再 merge_and_unload 导出 merged 模型、tokenizer、merged_sft_identity.json 和 weight_manifest.json。RL 准入在 `18-22` 要求 merged 身份文件存在、清单非空且清单所列文件 SHA 全部匹配。四个 RL 配置指向对应臂 merged 目录；本轮没有这些训练产物，不能实际启动 RL。

RL 重新加载 merged 全权重，再把新的 LoraConfig 交给 GRPOTrainer 的 peft_config（`114,151`），未把 SFT adapter 当成 RL adapter。设计上禁用新 RL adapter 应回到合并 SFT 权重；但代码没有显式 reference 数值断言，TRL/PEFT 在目标版本是否按预期禁用 adapter 必须现场验证，当前不能宣布 reference 验收成功。

GPU 应在固定 prefix/completion 上：①保存 merge SFT logits；②新 RL LoRA 创建后禁用 adapter，比对同 dtype/eval 下 logits；③更新 RL LoRA 后再次禁用，比对仍为原 SFT；④确认仅 RL adapter 有可训练参数，SFT 基座被冻结。若禁用后退回 E0、基座参数变化或 reference 随 RL 更新，立即停止。

### 2.5 RL prompt、奖励、mask 与两个归一化

RL 数据在 `approved_hf.py:132-145` 另造 prompt，只有 system 与题面（去掉前导 image 标记并 strip）；reference_answer 作为 reward 私有列。它没有复用 SFT 的 model_view，但显式列举了输入字段，当前没有答案直接进入 prompt 的代码。RL 配置中的 max_length 没有传给 GRPOConfig；它**不是已生效的 RL prompt 总长限制**。max_completion_length=2048 生效字段可见，max_prompt_length、temperature/top-p 等当前依赖所用 TRL 默认值，尚未验证。本轮模板 prefix 最长1248 tokens；目标环境要实际打印 RL 输入长度，避免隐含的 prompt 上限把题面裁掉，不能根据配置里的3800认为已经保护完整题面。

`math_reward:85-87` 把 worker.correct 变成 0/1，四个并发子进程最多各 20 秒；unsupported、解析错误与资源错误都会折为 0，status 没有写进 RL 训练日志。4 道关系式参考题会触发保守类型拒绝，有 boxed 回答也不能从这个奖励器得到 1。不能把它解释成模型不会做题。

参考算子定义：rewards `[Q,G]`，G=4。GRPO 为 A=(r−组均值)/(样本标准差+1e-8)，Dr.GRPO 为 A=r−组均值（`reference.py:17-26`）。例如 [1,0,0,0] 得 [1.5,-0.5,-0.5,-0.5] 与 [0.75,-0.25,-0.25,-0.25]；全同奖励的策略优势为零，有 KL 时总损失/梯度未必零。

token logp/old_logp/mask 可视为 `[Q,G,T]`，advantage `[Q,G]`；ratio=exp(logp−old_logp)，裁剪后逐 token 求和。参考 GRPO 按每条回答有效长度平均，Dr.GRPO 按固定常数 C≥T 归一化再跨回答平均（`reference.py:29-42`）。不传 mask 或把 pad 计入长度会改变梯度；不同回答长度的梯度检查见 `tests/test_losses_and_masks.py:29-41`，本轮通过。

工程入口显式传 loss_type=grpo/dr_grpo，scale_rewards=group/none、beta=0.04、mask_truncated_completions=True、disable_dropout=True、sync_ref_model=False（`approved_hf.py:143-151`）。参考算子不含 KL，不能称完整 TRL 数值复现。本轮环境没有 TRL，实际 epsilon、全局归一化分母、reference/KL、截断 mask 与奖励标准化次序均未验证；要固定目标源码再逐项对齐。截断 mask 通常用于排除未正常结束回答，但本轮只确认传参，不能将预期行为当已观测行为。若整组无有效 token、全同奖励比例极高或所有组被截断，应先判工程/奖励信号无效，不据此推断算法优劣。

### 2.7 数学评分与错误分类

`scripts/math_verify_v3_strict_worker.py:20-38` 只认证答案等价，不认证推导过程。`scripts/math_verify_pilot_worker.py:11-20` 遍历全文所有 boxed，不只末尾答案，所以 think 中的探索框也可能触发不同框门槛；较新的数据构造核验能力不会自动传到这个训练评分器。

当前类别应分别保留：

- equivalent / mismatch：在支持的表达式域内等价/不等价。
- relational_answer_requires_task_aware_manual_review：等式、不等式、关系式保守不支持，不证明错误。
- multiple_distinct_boxes_require_manual_collection_review：多个不同框，可能是集合或元组，不猜语义；单一集合表达式不是一概不支持，仍取决于 parser。
- missing_box / unclosed_box：格式或抽取失败；unparsed_reference / unparsed_prediction：参考或预测解析失败。
- verifier_error：外层超时/进程/JSON/依赖错误；worker 内异常可能直接以异常文字作为 status。需要保存更细原因，不能都归为数学错误。

本轮六个真实 worker 探针分别得到 equivalent、mismatch、missing_box、关系式不支持、多框待复核、unclosed_box，见 [token_audit.json](token_audit.json)。不是完整评分器覆盖验收，更未遍历所有最终测试答案来调规则。

评测 `scripts/evaluate_approved_math.py:17-28` 使用独占新建逐题输出、greedy、固定提示、tokens/预算触顶/verification 和 summary。它接受任意 --data，不验证评测白名单/封存 SHA，不冻结 adapter 权重或 tokenizer/template SHA，也不保存 GPU 成本。数据 SHA 在结束时记录，不是生成前准入。portable approved_evaluation_files=[]，math 数据另有 math_manifest 身份；正式评测需明确这两套身份的关系并先校验，而不是把训练 release manifest 当成已批准全部评测文件。

## 4. 问题排序

### A. 阻塞当前训练/上卡放行

1. **没有可用的项目完整依赖环境与 GPU 验收。** 默认 Python3.8 不兼容路径准入，学习环境 Transformers5 改变模板返回类型。优先建独立环境，不能把数据超长当作报错根因。GPU/驱动/显存本轮未检查，因为不属于本轮真实模型实验。
2. **RL 依赖的 merged SFT 权重尚不存在。** 正确顺序是先验收 SFT 和合并，再验收新 RL LoRA/reference；不能写占位身份文件绕过门槛。
3. **最长样本、真实 rollout、截断有效组与完整恢复尚未验收。** 2 步随机采样并不保证覆盖全量最长题，需要单独安排最长 batch 验收；CPU tensor 检查不能替代 A100。

### B. 影响实验可信度，正式实验前解决

1. **E0/E2/正式 E1/E3/E4 与统一评测协议未配置。** 当前只有两步 SFT 和 SFT后 RL；虽然代码分支允许 initial_state 非 sft，但没有 E2 起点准入、reference 身份和完整配置验收，不能称 E2 已实现跑通。
2. **RL 奖励丢失错误类型且有可确认的覆盖缺口。** 4 道关系式参考会自动拒绝；多框/解析/超时也归零。先做 train/dev 侧评分支持清单和状态计数，冻结版本；不据最终测试错题调整评分规则，不把候选加入白名单。
3. **身份链和恢复检查不足。** 缺 tokenizer/模板/评分器/真实起点权重的身份绑定，缺 checkpoint 完整性预检和同 horizon 恢复等价证据。
4. **运行时未主动查 dev 保护，评测未做文件准入。** 当前数据检查通过，但应在未来训练/评测入口形成拒绝条件；不重新划分现有 dev/test。
5. **长度、监督量和随机采样曝光不等价。** 同题同起点是必要条件；原生监督 token 约9.75倍，等步数不等训练 token。正式预登记等题曝光主比较并完整报告 token/成本，若增加等 token 比较，应单独定义预算，不能临时让某臂多跑。教师、提示、解法和长度共同变化，结论先限定为两套数据方案整体效果。
6. **RL 依赖默认参数、实际归一化和 mask 未核验。** 根配置 max_length 在 RL 不生效；显式冻结 prompt/completion 上限、采样、KL、优化/调度 horizon，核对实际 TRL batch/generation 语义和奖励标准差定义。
