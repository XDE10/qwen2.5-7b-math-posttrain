# 三周冲刺方案 v93（2026-11-09 → 12-02）

> 本文是 v93 的预注册方案：研究问题、固定配方、判定规则在看到结果之前写定。实现见 [experiments/qfft_v93/](../../experiments/qfft_v93/README.md)，面试材料见 [docs/interview/面试追问与参考答案.md](../interview/面试追问与参考答案.md)。

## 1. 研究问题

- **RQ1（QFFT 是否成立）**：同一份教师轨迹、同一配方，去掉题目训练（QFFT）相比常规 SFT，在 AIME24/25、AMC23、MATH-500 上的准确率是否持平，输出是否显著更短，长度是否随题目难度自适应。
- **RQ2（教师是否重要）**：DeepSeek-V4.1-Flash 新造的轨迹与 s1K-1.1 的 R1 轨迹，在同一 1000 题、同一管线下训练出的学生谁更强、谁更省 token。
- **RQ3（RL 能加多少）**：在 QFFT 模型上做 150 步 LoRA-GRPO，pass@1 是否提升；pass@k 曲线显示的是"磨尖已有能力"还是"扩大能力边界"；RL 会不会把 QFFT 的自适应长度冲掉。
- **RQ4（可选，起点之争）**：同样 GPU 时长下，QFFT 起点与 SFT 起点的 GRPO 谁收益更高。

## 2. 关键决策与理由

### 2.1 全参做 SFT/QFFT，LoRA 做 GRPO
- SFT 每条样本提供 O(token 数) 的监督，1000 条 × 约 1 万 token ≈ 1000 万监督 token；策略梯度每条 rollout 只有约 1 bit。Thinking Machines 的 LoRA Without Regret 显示 RL 下 rank 1 的 LoRA 都能追平全参，SFT 则在容量或 batch 偏大时落后。
- QFFT 官方、s1.1-7B、RomEscape 复现都是全参 LR 1e-5，全参能直接拿公开权重当锚点。
- 单卡 GRPO 用 LoRA：β=0 不需要参考模型，同卡 vLLM 每步只同步合并后的权重，没有第二份全参优化器状态。
- v26 不能证明"LoRA 不行"：它的 LR 2e-5 按 α/r 折算后仍比 LoRA 常用最优值（约为全参的 10 倍，≈1e-4）低约 2.5 倍，还叠加了 8K 窗口和 AIMO 数据。

### 2.2 不用 LLaMA-Factory 做主线
- LLaMA-Factory 能替代的只有 `train_sft.py`（约 300 行，已在 CPU 上验证断点续跑）。数据引擎、去污、判分、评测、GRPO、调度、分析这些占项目九成的部分它都不覆盖。
- Colab 镜像会变，LLaMA-Factory 对 transformers 有版本区间，再叠加 DeepSpeed 和 Liger，依赖冲突风险更大（项目历史上大量 GPU 时间花在依赖问题上）。
- QFFT 的核心就是一个数据格式。自己实现并用"与官方 S1_QFFT 数据逐字一致 1000/1000"和 token 级不变量来证明正确，比"用了作者的 yaml"更有说服力，也回答了"是不是调包侠"的疑问。
- 用框架本身不扣分。面试官看的是你是否理解并控制了 loss 掩码、梯度累积下的 loss 归一化、ZeRO offload 的显存账、检查点语义，这些在自己的训练脚本里都能讲清楚。

### 2.3 1000 题硬标准与超长题的处理
- 训练窗口从 16K 提到 32K，两位教师、两种格式都不截断。R1 轨迹最长 26,835 token，1000 条全部放得下；QFFT 官方 16K 截断会让 90 条轨迹在得出答案之前被截掉，这种序列教的是"长推理不收尾"，正是 v26 出现大量重复循环的可疑原因之一。直接丢弃超长题又会系统性地去掉难题。
- DeepSeek 一侧：每题取按时间顺序第一次可用的尝试；没有可用尝试的题由 `teacher fill` 继续采样（每题最多 8 次，v91 防重复提示词，effort 依次 high/high/max/...），直到 1000/1000。准入只看结构与长度，不看答案对错，与 s1K-1.1 和 QFFT 官方一致。
- 去污：规范化 13-gram + 序列相似度 ≥ 0.6，对 MATH-500、AIME24、AIME25、AMC23、GSM8K 全部检查，17 对命中已逐一人工复核。新发现 1 条泄漏：`s1k11/row/0918`（AIME 2002 I #12）与 MATH-500 `test/intermediate_algebra/1063.json` 是同一题换问法，轨迹里直接算出 1+274i，v93 用已批准的 OpenR1 原题池替换。其余 13 对只是"m/n 互素，求 m+n"一类句式相同。

### 2.4 对 DeepSeek-V4.1-Flash 质量的担心怎么回答
- 数据层：`teacher_report.md` 在同一批可核对题上比较两位教师的正确率、对错矩阵、长度、反思词频率。参照值：R1 在 s1K-1.1 的 742 道可核对题上答对 62.7%（Math-Verify，最终答案最后一个框）。
- 训练层：RQ2 的 2×2 矩阵直接比较学生。
- 如果 DS 的可核对正确率明显低于 R1（预注册阈值：低 5pp 以上），先跑 `teacher verify` 生成 `ds_verified` 变体（只替换"可核对且答错"的题），再决定主线用哪一份。这是公开 R1 数据做不到的：R1 轨迹是固定的，DS 可以按需重采样。

### 2.5 评测口径
- 所有模型同一组 prompt token，原生 RoPE，`max_model_len 32768`（不再用静态 YaRN），temperature 0.6、top_p 0.95，固定逐条种子。
- 只判最终段的最后一个 `\boxed{}`，Math-Verify 0.9.0；主指标不用 LLM 复核（单边复核只会把错改对，格式差的模型补得多）。
- 采样数：AIME24/25 各 16、AMC23 8、MATH-500 4、GSM8K 1。主结论看 AIME24+25+AMC23 合并的 100 题（单个 30 题的 AIME 年份 5pp 以内基本分辨不出）。
- Qwen2.5-Math-7B-Instruct 只支持 4096 位置，按它自己的上下文评测，作为外部参考，不作受控对照。

### 2.6 GRPO 配置
LoRA r32 全部线性层、LR 1e-5、150 步、每步 8 题 × 8 采样、temperature 1.0、`loss_type="dapo"`（token 级归一化）、β=0、clip-higher ε_high 0.28、截断样本不计 loss、奖励为最终段判分 0/1；题池 = 已批准的 920 题（E0 四次对 1–3 次）+ 637 题（E0 四次全错），启动时再对 v93 评测集去污。

## 4. GPU 预算（估算，以阶段 1 冒烟实测的 s/step 为准）

| 项 | H100 80GB | G4（RTX PRO 6000 Blackwell 96GB） |
|---|---|---|
| 每个全参 run（6 epoch，约 5–6 千万 token，375 步） | 约 5 h | 约 8 h |
| 每个长链模型完整评测（约 2,600 万输出 token） | 约 1.5 h | 约 2.5 h |
| GRPO 150 步（含合并） | 约 4 h | 约 6 h |
| 冒烟 + 锚点评测 | 约 6 h | 约 9 h |
| P0（阶段 0–4） | 约 23 h | 约 36 h |
| P0 + P1 + P2 | 约 40 h | 约 62 h |
| 计算单元费率（每小时） | 约 18.05 | 约 8.71 |
| P0 计算单元 | 约 415 | 约 314 |
| P0 + P1 + P2 计算单元 | 约 722 | 约 540 |

- 依据：RomEscape 在单张 RTX PRO 6000 + 251 GB 主机上跑同配方（ZeRO-2 offload、16K、6 epoch、batch 8）用了 35,174 秒；v93 有效 batch 16 让 CPU-Adam 步数减半。H100 的 bf16 算力与显存带宽都高于 G4（SXM 版约 2 倍，PCIe 版差距小一些），以冒烟实测为准；CPU-Adam 那部分取决于 VM 的 CPU 核数，与 GPU 无关。
- 显存：bf16 权重与梯度约 30 GB，32K 检查点激活与单层重算约 13 GB，Liger 消掉 logits 交叉熵的十几 GB，G4 与 H100 都有余量；主机内存约 122 GB（fp32 主权重 + Adam m/v + fp32 梯度），167 GB 可以承受。
- 费率：H100 high-RAM 约 18.05 计算单元/小时（[gkbrk.com 整理的 Colab 规格表](https://www.gkbrk.com/google-colab)，同表列出 H100 high-RAM 主机内存 230 GB、本地盘 235.7 GB，A100 high-RAM 主机内存 167.1 GB），G4 约 8.71 计算单元/小时（[Chris McCormick 2026-03-10 的实测表](https://mccormickml.com/2024/04/23/colab-gpus-features-and-pricing/)）。这些是第三方整理的数字，费率会变，以 `colab usage` 为准。Colab Pro+ 每月含 500 个计算单元（[Google Workspace Updates](http://workspaceupdates.googleblog.com/2024/06/google-workspace-colab-pro-and-colab-pro-plus.html)）。
- 建议（v93-P5 起为默认）：所有 GPU 阶段先用 G4、分不到再用 H100。按上表估算，G4 少用约两到三成计算单元（每个全参 run 约 70 对 90，全部阶段约 540 对 722），显存还多 16 GB；H100 每小时快，只在赶时间时用。全参训练里 CPU-Adam 那部分与 GPU 无关，H100 的实际加速可能小于纯算力比，冒烟实测后再修正上表。按 G4 估算，P0 + P1 约 500 个计算单元，接近一个月的额度；P2 可能要另买计算单元，开跑前用 `colab usage` 看余额。若 Colab Pro+ 允许并行会话，锚点评测可以和训练同时跑。

**冒烟后修订（2026-11-09，阶段 1 在 G4 上 41 分钟跑通）**：上表是冒烟前的估算。实测 32K 最坏长度全参 142 s/步、显存峰值 28.9 GiB（保留 42.6）、主机 RSS 145.3 GiB / 177 GiB、本地存检查点 113.5 GiB 用 386 s，GRPO 最坏长度 476 s/步、66.6 GiB。真实数据每步 token 只有冒烟的 13%（DS）到 30%（R1），但每个微批的 ZeRO-2 梯度卸载开销冒烟测不出，所以每个全参 run 的训练按 2.7–7.9 h（DS）、4.3–11 h（R1）估，评测另加 1–2.5 h，以第一个 run 的 s/step 为准；公式和预算见 [交接文档第 5 节](../handover/kiro_ide_onboarding.md)。另外 Google Drive 每个账号每 24 小时约 750 GiB 上传上限，全参改为每 2 个 epoch 存一次（每个 run 约 241 GiB），24 小时内最多 2 个全参 run。

## 6. 决策点（预注册）

- **D1（11/14）**：`qfft_ds` 与 `sft_ds` 在 AIME24+25+AMC23 合并 100 题上的差在 ±3pp 以内、平均 token 少 30% 以上，RQ1 判为"复现"，RL 用 `qfft_ds` 起点。两者在 MATH-500 上都比 E0 低 2pp 以上，先排查管线（模板、分隔符、loss 曲线对照 s1.1-7B 的公开 TensorBoard），不进 RL。
- **D2（11/17）**：reward 上升而评测不动，做 pass@k 分析（"RL 只磨尖"本身就是结论）；`frac_reward_zero_std` 持续高于 0.6，换更难的题池；平均长度持续上涨，降温度或改 Dr.GRPO 的常数归一化。
- 不按评测结果挑 checkpoint，一律用最后一个 epoch / 最后一步。

## 8. 风险与预案

| 风险 | 预案 |
|---|---|
| Colab 分不到 G4/H100 | 两种卡都支持，默认 `--gpu G4,H100`，加 `--wait-min N` 按顺序重试；A100 显存够，但 VM 主机内存低于 128 GiB 时训练阶段会直接报错（CPU offload 需要约 122 GB），那时 A100 只用来评测；40GB 卡放不下全参 32K，只能改 LoRA r64、LR 1e-4 |
| 主机内存不足（CPU offload OOM） | 确认 `--high-mem`；冒烟看 `host/rss_gib`；仍不够就冻结 embedding（省约 9 GB 主机内存，需记为配方变更） |
| 122 GB 镜像写 Drive 太慢或写不进去 | rclone 挂载的写缓存放不下约 91 GB 的单个优化器文件，所以镜像用 `rclone copy` 流式上传、在后台进行、失败不影响训练；被取代的镜像永久删除，不占回收站；最坏情况只能从更早的镜像恢复。第一份镜像（第 126 步）完成后在 `colab-reports` 的 `saves.jsonl` 与日志里确认上传耗时 |
| vLLM / TRL 版本在 Colab 上装不上 | 依赖装在独立 uv 虚拟环境；首次成功后快照到 Drive 并冻结版本清单 |
| DS 轨迹质量明显不如 R1 | 按 2.4 生成 `ds_verified`；RQ2 的结论照实写 |
| GRPO 收益小 | 结论改为 pass@k 与长度的机制分析；RL 曲线和失败分析照样能写 |
