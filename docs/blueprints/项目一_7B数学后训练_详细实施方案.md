## 1. 项目做什么，最后交付什么

主模型固定为 `Qwen/Qwen2.5-7B-Instruct`，研究三个问题：高质量 SFT 冷启动是否优于直接 RL；GRPO 与 Dr.GRPO 的归一化差异如何影响正确率和回答长度；动态过滤是否值得额外生成成本。

核心数据模块另研究：在同一接受题集合上，固定OpenR1快照的原生轨迹与本次DeepSeek API盲生成精炼解答，怎样影响受限推理预算下的准确率、长度、截断和成本。沿用E7编号，但由可选数据消融提升为核心研究模块；不预设精炼版获胜，不将教师年代或API品牌当成效果解释。

1.5B 实验作为历史诊断归档，不再作为升级前置条件。它不证明模型容量是退化根因。7B 实验重新建立数据、提示、评分与资源基线，不直接把两种规模的非受控成绩差异解释成规模效应。

最终交付：数据 manifest 与去重报告、训练/恢复入口、五个核心评测状态、逐题预测、训练曲线、成本报告、失败案例、可复现实验说明。成功标准是可信回答研究问题，而非保证涨点。

## 3. 数据配置与划分

### 3.1 SFT：目标 1500 条，而非硬凑数量

首选 `open-r1/OpenR1-Math-220k`，第一轮只用一种来源。每题可能有多条轨迹，逐轨迹检查验证结果、完整性与结束原因；一道题至少有正确轨迹不代表全部正确。

处理顺序：固定快照 → 抽取题目/解答/标准答案 → 对评测集去重 → 题目级划分 → 挑选正确完整轨迹 → 目标 tokenizer 计数 → 人工抽查 → 封存。

- 2026-10-23 修订：第一轮紧凑候选回答长度为 **500～1600 token（含边界）**，按固定 revision 的 Qwen2.5-7B tokenizer 对完整回答计数，包含 `<think>`、最终答案和实际输出内容。另检查题目＋chat template＋回答/EOS 的总长度不超过 SFT 4096。范围是资源与风格筛选条件，不是质量标准，也不保证 RL 2048 下不截断；按题型/来源/长度报告筛选偏差，pilot 实测后再冻结正式预算。
- 筛选单位是轨迹索引 i：`generations[i]`、`is_reasoning_complete[i]`、`correctness_math_verify[i]` 必须严格对应，三列长度不一致或标记缺失则隔离，不能用整题 `correctness_count>0` 代替。`finish_reasons` 若存在须检查是否与轨迹一一对应及是否截断；字段缺失不伪造结束原因，另做文本结构/最终答案完整性检查。此轮仅接收 math-verify 明确为 true 的轨迹，不将 LLM judge 的通过等同于数学验证。
- 每题先保留一条轨迹，避免某题重复多次造成隐性加权。
- 不截断长回答后继续把它当完整正确样本；超长样本独立记录。
- 按题型、难度、长度分桶，报告筛选前后分布和实际通过数量。
- 人工抽查至少 50 条，覆盖各长度桶与题型；发现系统问题则回到筛选步骤。
- `Bespoke-Stratos-17k`、`NuminaMath-CoT` 只作为后续数据来源消融，第一轮不混合。

### 3.2 RL：先 MATH train，后考虑 DAPO

第一版使用 `DigitalLearningGmbH/MATH-lighteval` 的 train（7500 题），先按题目去重及封存 dev，再建立候选训练池。`BytedTsinghua-SIA/DAPO-Math-17k` 为扩展，需核查来源及答案类型，不直接混入。

建议预先划出 256 道 dev，仅用于选模；其余构成候选池。SFT 来源中与 dev、最终测试同题或近重复的记录一并移除。明确记录 SFT 与 RL train 之间允许多少重叠；如果允许，要报告数量与分析影响。

2026-10-23 已封存的唯一数学 dev 为 `data/math/math_dev.jsonl`（256 题），候选池为 `data/math/math_train.jsonl`（7184 题），文件 SHA256 以 `data/math_manifest.json` 为准。项目二必须复用这两个文件及身份，不重新抽 dev；筛选脚本先验证哈希且不覆盖原文件。7184 是当前词法去重后的候选数，不代表逐题质量审核或零污染证明。

用原始 7B 在候选池固定温度采样四次，优先取 1～3 次正确的题，目标最多 3000 道。这里是经验正确比例 25%～75%，不是 pass@4。四次全错不证明永远无法解决；未达到 3000 条时报告实际数量，不偷偷放宽标准。

主比较共享同一候选池、题目列表和筛选模型。动态过滤只在单独实验中启用；记录被拒组、重采样次数、总生成 token 和采样开销。

### 3.4 强模型离线蒸馏与定向增广

2026-10-23 复核：E7 的 1500 条是目标上限；若新教师仅有较少可信接受样本，两组都使用该相同题目交集，不补入不同题目凑数。换教师还可能改变正确性、长度与监督 token，不能只凭同题宣称纯风格因果。E8 禁止从当前 dev 错题直接换数/改写增广；可以据 dev 的题型级诊断，从 train 诊断池选择同类型种子，且所有后代继承 train。若改变旧 dev 用途，先迁移版本并另封存新 dev。

新增明确的数据工程主线：公开 train 题作为种子，调用选定 GLM/DeepSeek 教师生成可见解答，再独立验证，形成自己的派生 SFT 数据。先小试 50 题，再扩大到最多 1500 条接受样本，不用 API 数量代替质量证据。

生成器只收到题目、输出格式与长度要求，不收到标准答案或公开解答。验证器离线对比参考答案，用可计算判据复核算术/代数，抽查步骤正确性；解答不完整、冲突答案、错误前提均拒绝。执行共用规范第 4.1 节的盲生成硬约束：本版禁止 answer-conditioned 解答进入训练候选，默认每题最多生成 3 次，失败后不以正确答案提示修复。答案相同不构成过程正确的证明。

核心数据对照 E7：同一批原题分别使用公开解答与新教师解答，固定学生起点和更新设置，并报告实际监督 token 差异。若只接受部分教师解答，公开对照也使用相同接受题集合，避免筛掉难题造成假增益。E7 是两个 SFT 作业；只有题集合/预算完全相同时才能复用 E1 作为其中一个。核心 E0～E4 的算法比较仍共享同一版 SFT 起点，不中途替换数据。

2026-10-23执行约定：主力仅`deepseek-flash`，`thinking.type=disabled`、temperature=0.4、API输出上限2400；使用可检查的书面解答，`<think>`仅为序列化包装，不解释成真实内部反思。固定system与完整payload见`data/compact_distillation_v2_20261023/policy.json`。Qwen2.5-7B tokenizer测量合成回答150～1500、完整模板≤3800；不填充短证明，不截断超长答案。首次生成及最多两次盲重采样，生成器不能接收答案/原解答/验证反馈；Pro补采暂不启用，若启用必须另立混合教师实验。

确定性门槛只检验停止、结构、长度、噪声和Math-Verify答案等价，不能证明过程正确。允许对已有完整书面解答做有记录的包装/成对显示定界符规范化，保留原始输出、全部boxed数学文本及操作日志；不补造关键步骤，不删除冲突结论。人工审核仍pending，AI抽查与自动银标候选分别记录。难度打标36%一致率已归档，不再批量调用estimated_level；不再全量调用LLM过程裁判，但保留分层过程审核门槛。

本轮旧50题144条缓存已零调用重验；独立新40题共118次生成，首次答案验证26/40、至少一次29/40，冻结格式准入仅1/40。初版解析器对LaTeX显示定界符/标签外正文过严，已保留其原结果并另列事后格式兼容复审：旧缓存严格18/50、规范化27/50；新pilot严格18/40、规范化19/40。事后复审不冒充冻结验收通过，也不能把自动候选当推导金标。源题缺图/推导错误仍由审核隔离；未扩至1200/1500题、未批准训练。详见[本轮执行报告](<../reports/compact_distillation_v2_20261023/执行报告.md>)。

教师返回字段仅为API别名，未提供可验证的不可变底层checkpoint；记录请求/响应、日期、配置与缓存身份，不写成“2025 vs 2026代际差异”的受控结论。同题也未单独控制解法、风格、长度和监督量，主要结论先表述为精炼数据方案整体效果。所有比较模型使用同一组2048/3072/4096预算（按资源选择并预登记）；先看dev再冻结最终测试，不只给某组更多tokens。短SFT示范不能保证RL2048不截断。

定向增广 E8：种子严格仅来自 train 内划出的诊断池，再生成最多 500 道候选变式；当前 dev 的具体题面及其改写不进入训练。新题必须重新求解并验证，不继承原答案；同构/换数题保留 parent/family ID，全部后代继承训练划分。禁止将任何 MATH-500、GSM8K-test 题目、错题、解答或改写放入生成请求。若未来转换旧 dev 用途，须执行共用规范的数据版本迁移和重新留出规则。

候选入库前对 dev/test 执行独立的只读去重检查：规范化精确哈希 → token n-gram Jaccard（规模较大时用 MinHash 候选检索）→ 对实体/数字占位化文本的相似检查 → 可疑同构题复核。相似度阈值在训练侧的重复/非重复样例上校准并冻结，保存算法版本、阈值、命中 ID 和处置理由；高相似不能直接等同重复，低相似也不证明无污染。检查器可读取评测题用于排除，生成器不能接收这些内容；命中后隔离/剔除，不根据命中的测试题继续改写绕过检测。

E8 至少比较“相同起点＋等量普通题追加训练”和“相同起点＋定向题追加训练”，共两个作业，统一追加预算并保留无追加训练状态。它与 E7 分阶段实施，不同时改变解答质量、题目数量、学习率和算法。合成数据有益与否由这些对照决定，不预设一定修复短板。

算法核心E1～E4为4次训练；核心数据对照E7另需2次SFT，若其公开对照与E1的题集合/监督版本/预算完全一致可复用一次，因此完整核心研究共5或6次训练，不含smoke、失败重跑和多种子。E8仍为可选、另增2次。先完成E7的数据准入，再冻结唯一E1和E3/E4起点，避免中途替换数据破坏算法对照。

## 4. 到哪里测：基准、工具与排行榜

数据方案补充：执行 [强模型合成数据与验证共用规范](<共用规范_强模型合成数据与验证.md>)，保留公开数据基线，并按第 3.4 节开展独立的数据实验。

**MATH-500 是评测数据集，不是把权重上传后自动打分的网站。** 本项目首先在本地/Colab 运行固定协议，公开报告；公开排行榜提交是可选工作，需要另查当时的提交规则。

- 主基准：`HuggingFaceH4/MATH-500`，500 题，配置冻结后最终评测。报告整体准确率、题型/难度分组及逐题结果。
- 保持能力：`openai/gsm8k` 的 main/test，1319 题。旧的 128 题仅作历史诊断，不作为 7B 新留出集。
- 日常选模：前述 256 题 dev，绝不从 MATH-500 中切选模题。
- 数学验证：用固定版本 Math-Verify 或等价实现处理表达式、分数、根式；GSM8K 数字解析器不能直接覆盖所有 MATH 答案。
- 评测入口：项目内统一生成与判分脚本；借鉴 Open R1 的评测实现。必须记录模板、生成引擎、答案抽取与验证版本，不能仅写“用官方脚本”。
- 公开模型卡/论文分数只作背景，只有模型、数据、模板、推理预算和评分规则一致时才进行直接比较。没有提交不能写“上榜”。

主协议：统一贪心单次回答，统一提示、最大输入长度和最大输出预算；起始主预算建议 2048。4096 作为所有模型都参与的预算扩展，不能只给最佳模型。若 dev 证明 2048 大量截断，应在最终测试前整体修改并冻结协议。

报告答案正确率、解析失败率、严格格式率、截断率、正确/错误回答长度、GPU 时间及 token/s。带标记正确率与宽松匹配率分开，主评分规则预先固定。按题目进行配对 bootstrap 区间；它不替代多个训练种子。

## 5. 要做几个实验

### 5.1 核心版：5 个状态，4 个训练作业

1. E0：原始 7B Instruct，无训练。
2. E1：E0 → SFT，保存唯一冷启动检查点。
3. E2：E0 → GRPO，回答直接 RL 是否有效。
4. E3：E1 → GRPO，与 E2 比较冷启动；与 E1 比较 RL 增益。
5. E4：E1 → Dr.GRPO，与 E3 比较归一化设计。

核心训练作业为 E1、E2、E3、E4；E3/E4 共享 E1 起点。原始官方 Math 模型为额外参考评测，不增加训练作业。预算不足时 E0～E3 是阶段成果，但未完成 Dr.GRPO 研究。

### 5.2 推荐扩展：再加 2 个训练作业

- E5：E0 → Dr.GRPO，补全起点×算法的两因素比较。
- E6：E1 → Dr.GRPO＋动态过滤，与 E4 仅差过滤策略。

因此核心版 4 次训练，扩展版 6 次训练，不含 smoke、失败重跑和随机种子复现。主结论最好使用 3 个训练种子；共享 SFT 起点的算法复现只反映 RL 随机性，端到端复现还要重训对应 SFT。

## 6. 起始超参数与控制变量

SFT 建议：学习率 `1e-5`，1 epoch 起步，micro-batch 1、有效 batch 16、总长度 4096，回答部分计算损失，启用梯度检查点。先检查 prompt、padding、EOS、shift 和最长样本；若修改 batch，记录等效更新量。

RL 建议：学习率 `5e-6`，每题 4 条回答，temperature 0.8、top-p 0.95，最大回答 2048，KL 系数起始 0.02，每 rollout 一轮更新；先做 20 更新 pilot，再以 100/200 更新作为中程检查点。正式预算可按预先登记规则扩展到 400/600 更新，不把 200 步当作收敛保证或硬上限。

每次更新目标累计 4 道题、16 个回答；将其映射到所锁 TRL 版本的实际 batch/梯度累积语义并用日志核对，不能机械套字段。各组记录实际题目数、回答数、有效 token 数。

200/400/600 更新分别约为 800/1600/2400 次题目曝光、3200/6400/9600 条训练回答；曝光次数不等于唯一题数，也不含筛选时丢弃的 rollout。日志另存 unique problem 数、重复率、重采样与总生成量。

扩展规则在最终测试前冻结：先核查梯度/奖励有效性、截断和评分；若 dev 仍有改善、没有明显训练/验证分离且预算足够，E3/E4 成对延长，并保留共同步数结果。无差异可能来自效应小、评测噪声、学习率、数据或实现，不直接判成欠拟合；训练更久也不保证显现差异。学习率调度的总步数提前确定；若改变调度 horizon，标记新配置并对照复跑，不能把临时改总步数称为严格续跑。rank 变化另开消融，不与延长训练同时修改。

GRPO 显式选择 `loss_type="grpo"` 与组内奖励标准差缩放；Dr.GRPO 选择 `loss_type="dr_grpo"` 并关闭该缩放。对应版本可能用布尔值或枚举，执行前查 API，不依赖默认值。

奖励先只使用答案正确性 0/1，格式独立记录。参考策略固定为各自 RL 起点；E3/E4 使用同一 SFT 参考。LoRA 禁用后是否真回到该参考必须测试，不允许误回原始 E0。

所有组统一截断样本的奖励、mask、EOS 与长度处理规则。Dr.GRPO 固定归一化常数与最大回答长度有关，变长实验应单独报告。

## 7. 你亲手完成的核心工作

1. 数据工程：自己实现筛选/划分/去重，手工追踪一条题目从源记录到训练样本；产出审计 JSON。
2. SFT 原理：打印两个样本的 input IDs、labels 和 mask，解释为什么只监督回答；写微型测试验证梯度覆盖。
3. GRPO 数学：手算四个奖励的均值、标准差与优势，再实现独立小张量版本，与框架比对。理解全同奖励、KL、裁剪和重要性比率。
4. Dr.GRPO：在同一批 token loss 上实现两种归一化，构造不同长度样例，验证公式差异；不要为了学习重写整个训练器。
5. 评测：自己写至少 20 个解析反例，包括冲突答案、根式、分数和截断；保存原始输出与失败原因。
6. 工程：主动中断一次训练并恢复，核对步数、学习率、优化器和评测续跑。区分 adapter 与完整恢复检查点。
7. 分析：人工分析至少 30 个改善/退化案例，关联奖励、长度、题型，形成可复述的解释。

可直接复用框架的部分：分布式通信、自动微分、优化器、LoRA 注入、基础生成内核。你负责验证数据流和算法语义，不能只会改 YAML。
