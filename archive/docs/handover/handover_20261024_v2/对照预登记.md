# formal_v1 对照预登记草稿

所有配置均为 **草稿，未冻结**。v2准入遇到draft=true直接拒绝执行；这不是通过改变一个标志即可完成的数据审批或实验冻结。

## 1. 两种预算回答不同的问题

固定1500个同题pair、同一E0 revision、tokenizer/模板、LoRA rank16/alpha32/dropout0、seed42和逐题评测协议。原生与精炼的完整监督token总量实测为3,516,983和360,882（9.7455207倍），统计包含模板回答末尾EOS及换行，不含prompt或padding。label位置还按next-token shift扣掉首位置；由于首位置是prompt，数值与原统计相同。

**A：等题曝光。** 两臂各1500题、1 epoch、microbatch1、梯度累积16，末尾不足16的batch也更新；计划各94次optimizer更新。原生监督量3,516,983，精炼360,882，实际耗时和token成本可以不同。回答“在相同题目曝光下，两套数据方案怎样影响能力与成本”；不能宣称控制了监督量。

**B：等监督token。** 共同目标3,516,983，只在optimizer更新边界达到或超过目标后停止，不切掉回答或EOS来凑预算，报告超额。预先声明的模拟顺序为 `random.Random(42+epoch).shuffle`，单设备、每16题一更新、每epoch末尾flush：原生1 epoch/1500曝光/94更新，精炼9.757333 epoch/14636曝光/917更新，实际模拟监督3,517,814、超额831（约0.024%）。

917是明确顺序下的CPU预算模拟，**不是HF训练实测步数**。当前执行器没有实现这套确定性采样与按监督token停止的回调，因此B配置不可冻结。若采用其他sampler，必须在训练前重算和固定预算，不能训练后修改停止规则。学习率调度horizon也要在执行前固定；每次改变horizon另开配置。

B同时改变题目重复次数和optimizer更新数，可能带来重复学习、过拟合或优化差异；它不单独识别“更短轨迹”的因果。两个预算策略分别报告，不混算一个总平均，也不只展示获胜的策略。教师、提示、解法与长度仍共同变化，主结论限定为两套数据方案的整体差异。

## 2. 完整矩阵及共享关系

每种预算目录均含 `E0_shared.draft.json`、E1_raw/compact、E2_shared、E3_raw/compact、E4_raw/compact，以及 `experiment_matrix.draft.json`。这将E0～E4核心状态与两臂轴明确展开，E2无SFT臂，标为shared。

- E0：原始 `Qwen/Qwen2.5-7B-Instruct`，revision `a09a35458c702b33eeacc393d103063234e8bc28`。无训练；先dev256，冻结后统一MATH-500与GSM8K-test。greedy，回答预算2048，prompt预算1752，固定system指令。
- E1_raw / E1_compact：相同E0分别读取对应批准文件；seed42、LoRA rank16、学习率草稿1e-5。训练中没有rollout采样；只按A或B的预算协议优化。输出各自唯一正式merged身份，不能复用2步smoke充当正式E1。
- E2_shared：E0直接GRPO，reference=E0。数据是待筛选、待另行批准的统一RL池，**不是已批准的4810文件**。seed42、学习率草稿5e-6、temperature0.8/top_p0.95/top_k0，每题4条、prompt1752/completion2048、beta0.04、group奖励缩放、截断规则固定。
- E3_raw / E3_compact：对应E1→GRPO；模型与reference均绑定对应E1精确权重，RL新LoRA。其余RL池、seed、采样和预算与E2/E4一致。
- E4_raw / E4_compact：与同臂E3共享同一E1及reference，使用dr_grpo、scale_rewards=none；不能同时改数据、prompt、token上限、KL或动态过滤。

E2若跨A/B完全同模型、RL池、协议及预算，可复用同一实际run并列出引用身份；不能重复计为两次独立证据。E3与E4在每臂内严格共享起点；两臂E1本身并不相同。单种子42只是首版，不能声称多种子稳定性。

RL草稿先20更新工程/信号pilot，再比较共同100/200检查点；400/600只按预登记dev与预算规则成对扩展。没有将200更新当作收敛保证。动态过滤不混入首版算法比较。

## 3. 评分、身份与冻结条件

当前已有评分是strict-v3+audited-status-v2；关系式、多框等支持缺口单列，资源错误中止，不计答错。RL池筛选需要先冻结支持范围充分的任务感知评分版本；该版本本轮**未冻结、未验证**。不得先用有关系式拒绝偏差的0/1分筛池，再换评分器比较算法。

`identities.draft.json` 保存当前批准训练文件与dev/MATH-500/GSM8K文件身份；不扩大portable manifest的evaluation数组。模型、tokenizer/模板、评分器源码、merged清单及run配置最终由v2身份链记录。最终测试不用于改阈值、扩题、选模或修改评分规则。

冻结前仍需：Colab真实最长batch、reference、有效rollout和同horizon恢复验收；完成候选近似命中复核与正式RL审批；实现B的token计数/采样/停止验证；固定完整Linux环境、评分器、实际checkpoint起点和评测命令。上述未完成项保留未验证状态。

各run统一报告：可评分率与正确率、解析/unsupported/资源错误、截断、回答长度、实际监督/生成tokens、题目曝光/unique题数、optimizer更新、GPU显存/时间/成本；能力差异做逐题配对分析，保留退化和无提升结果。
